## 二、新增文档的门槛

**默认答案是「不新建」。**

满足下面**全部三条**才新建：

1. **现有文档里加一节会破坏它的主题**
   例：`LTSC-CHANGES.md` 讲「相对上游改了什么」，如果硬塞进「怎么构建打包」，
   主题就散了 —— 所以 `BUILD.md` 单独存在是对的。
   反过来，如果只是想给 `BUILD.md` 补一条常见错误，那就加一节，不新建。

2. **能说清「谁会看、什么时候看」**
   答不出具体场景，说明它更可能是过程记录，应该放仓库外的 `docs/`。

3. **它不是某次工作的过程记录**
   「某天做了什么、当时的判断是什么、证据链怎么走的」——这类归仓库外。
   见第三节。

**不构成新建理由的**：

| 想法 | 为什么不新建 |
|---|---|
| 「这个文件太长了，拆开好读」 | 长度不是理由。1186 行的 MASTER-PLAN 有明确的章节导航，不需要拆 |
| 「按主题分类更整齐」 | 分类不是目的。文档是给人查的，不是给目录看的 |
| 「以后可能会用到」 | 用到再建。空壳文档比没有更糟，它会让人以为那里有内容 |

**数量不是指标。** 历史上曾有一条「`src/docs/` 不超过 10 份」的规定，
后来发现那会逼着人把不同主题的文件硬合并，与「一份文档只讲一件事」直接冲突，
**该规定已撤销**。判断标准是「有没有两份讲同一件事」，不是数几份。

## 三、入库标准：什么进 git，什么留在仓库外

| | 进 `src/docs/`（git） | 留 `docs/`（仓库外） |
|---|---|---|
| **判据** | 对外有用：别人拿到这个仓库会需要的 | 过程记录：我们自己怎么得出某个结论的 |
| 典型内容 | 构建方法、恢复方法、稳定性论证、已知问题、改动清单、规范调研 | 某天的审计报告、当时的判断、证据台账、待办清单、决策过程 |
| 例子 | `BUILD.md` / `REMOVED.md` / `STABILITY-CASE.md` / `COMMUNITY-BUGS.md` | `stability-audit.md` / `verification.md` / `Citation Ledger.md` / `decisions.md` / `PRIORITY.md` |

### 为什么这么分

- **仓库外的内容会消失**。它不在版本库里，换机器、清目录就没了。
  所以**必须长期保留的对外材料不能放那里**——`REMOVED.md` 和 `STABILITY-CASE.md`
  就是 2026-11-17 从仓库外移进来的，原因是「对外有用但进不了版本库」。
- **仓库内的内容要经得起外部审视**。写进 git 的东西，别人会当权威读。
  带「未经复核」「当时判断」这类限定语的材料放进去会误导人。

| 文件 | 性质 | 状态 |

## 四、改文档时的两条硬规矩

这两条是这个项目踩过坑总结出来的，改任何文档都适用：

1. **结论被推翻，改写而不是删除**——写清「原来是什么、为什么改、现在是什么」。
   旧的理解不抹掉。见 `LTSC-CHANGES.md` 里「不改 AssemblyName」那条的处理。

2. **不要写会过期的固定数字**。
   提交数、文件数、行数这类每次提交都在变的量，**给命令而不是给值**。
   这个项目在同一件事上栽过三次（见 `LTSC-BASELINE.md` 的「数字为什么不该固定」）。
   必须给绝对值时，写清「截至哪个 commit」。
