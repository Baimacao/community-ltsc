## DEF-01 多指书写卡顿

**状态**：后期迭代
**记录日期**：2026-11-12

### 现象
用户反馈「多指比单指稍微卡一点，五指一起就更卡，写着写着越来越卡」。
但 2026-11-12 班级实机跑完整一节课，结论是「卡顿不明显」。

### 为什么推后
1. **没有可复现的症状** —— 现在改触摸层，改完也验证不了。
2. **根因未确认** —— ICC 在 MW_TouchEvents.cs 里自建了一套按 device ID 的
   `StrokeVisualList` / `VisualCanvasList` 结构。多指路径最可能卡在这里，
   但这是推测，没有数据支撑。
3. **改造成本高** —— 换输入层会动整条链路：
   主进程(.NET 8 x64) → IPC → IACore 辅助进程(x86/.NET 4.7.2) → InkCanvas

### 调研过什么
读了 inkeys3 源码（C++，711 个 .h / 87 个 .cpp，Direct2D 自绘）。
**结论是它的做法不能直接照搬**：inkeys3 用 Windows 的 `IRealTimeStylus` (RTS)
把触摸统一转成笔事件流，自己不维护任何按 device ID 的视觉结构，
所以天然没有"多指状态机"这类问题。而 ICC 走的是 WPF InkCanvas + 自建多点管理，
架构不同，照搬会重写输入层。

### 重启这项工作的第一步
**不要先改代码。先拿数据。**

LTSC P2 已在 `Helpers/InkPerfProbe.cs` 里加了慢笔现场快照：
单笔耗时 ≥120ms 时会立刻写一条

```
[P2卡顿] 第 N 次慢笔 Xms | 笔序=... 均=... | dec=a/max 笔画视觉=n 视觉画布=n 落笔点=n 僵尸清理=n 静默释放=n GC=n 工作集=nMB
```

判断方法：
- `dec` 和 `笔画视觉` 同步上升 → 真多指并发，属负载问题，考虑降采样/合并
- `dec=0` 但 `笔画视觉` 不为 0 → 状态机残留，清理逻辑有漏洞
- `僵尸清理` 涨得快 → 状态机已被污染，先修清理
- GC 次数在慢笔瞬间跳 → GC 抖动，查分配
- `工作集` 持续变大 → 内存泄漏

**等下次真卡了，拿这条日志说话，再动手。**

## DEF-02 UIAccess 引导流程

**状态**：后期迭代
**记录日期**：2026-11-12

### 现象
「窗口置顶」想覆盖任务栏时，现在只能靠管理员权限（代价是 PPT 联动失效）。

### 为什么推后
UIAccess 才是正解（不需要管理员，能覆盖任务栏），但落地需要两个前提：
1. **数字签名证书** —— UIAccess 程序必须签名，否则系统不认
2. **用户手动把 exe 放进受信任目录** —— 这是 Windows 的硬性要求，无法自动化

代码里 `Helpers/UIAccessHelper.cs` 已有 500+ 行完整支持，
等有签名证书后接引导流程即可。

### 当前替代方案
「重启到管理员模式（用于覆盖任务栏）」—— 文案已说清代价，
且新增的管理员权限提醒弹窗会在启动时告知 PPT 联动会失效。
